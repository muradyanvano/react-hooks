# Storybook

Operational rules for the consumer-facing Storybook documentation environment.

- Document public package behavior only. Stories import from `@muradyanvano/react-hooks`, never from internal hook paths.
- Keep the Storybook Vite alias scoped to Storybook/development configuration.
- Present examples with the shared `ExampleShowcase` system: polished preview, Show/Hide code, Copy code, and curated snippets.
- Prefer Controls for real options (`enabled`, `eventType`, `capture`, `dedupe`, `passive`, `once`, `delay`, `distanceThreshold`, `button`, `self`) and Actions/event logs for handler calls.
- For event-listener examples, show omitted-window vs explicit-target SSR guidance honestly, and prefer accessible interactive targets over pointer-only regions.
- For keyboard examples, document shortcuts, keep focus rings visible, avoid trapping focus, and use predicates when character shortcuts should not fire while typing in inputs.
- For typing-intent examples (`useOnStartTyping`): show search-focus and command-palette flows without turning them into shortcut demos; demonstrate editable blocking vs non-editable acceptance; map serializable Storybook modes to validators instead of exposing function controls; use controlled `KeyboardEvent` dispatch in play tests for modifiers/repeat; keep contenteditable regions named (`role="textbox"` + accessible name); status updates should use `aria-live`.
- For media-device examples (`useDevicesList`): use Storybook-only deterministic mocks with install/uninstall isolation for automated stories; re-install during render after Strict Mode cleanup (`useState` init alone is not enough); patch `navigator.mediaDevices` rather than replacing the whole `navigator`; prefer explicit Allow-access buttons over `requestPermissions: true`; show empty-label → labeled transitions and “temporary tracks stopped” privacy confirmation; simulate `devicechange` connect/remove; keep mocks out of `dist`/tarball. One opt-in **Live hardware** story may use real `navigator.mediaDevices` for local manual testing — never auto-prompt, never click Allow in play tests, document that pages cannot revoke camera/mic in most browsers (site settings + remount), and keep Remove-permission UI best-effort only.
- For screen-capture examples (`useDisplayMedia`): keep exactly one **Live screen sharing** story on the real API — button label `Start sharing my screen`, calls `start()` directly from the click with no artificial delay, and documents that the browser will ask what to share; its play test must never click start, only assert visible UI and unsupported messaging. Every other story (Overview, Video preview, System audio, Browser-ended sharing, Permission cancelled, Error recovery, Stream replacement, Enabled state, Unsupported browser, Playground) uses a Storybook-only `getDisplayMedia` mock with the same install-in-`useState`/re-install-during-render/uninstall-in-cleanup pattern as `useDevicesList`, patching only `navigator.mediaDevices.getDisplayMedia`. Attach the returned stream to `<video>` via a `srcObject` effect, never `URL.createObjectURL(stream)`.
- For user-media examples (`useUserMedia`): keep exactly one **Live camera** story on the real API — button label exactly `Start camera`, call `start()` from the click, muted `autoPlay` `playsInline` preview via `srcObject`, no auto-start, play test never clicks Start. Every other story uses Storybook-only `userMediaMock` patching `getUserMedia` (preserve `enumerateDevices` for device-selection). Cover overview, video/mic/both, device selection with `useDevicesList`, facing mode, resolution, autoSwitch vs manual restart, enabled, permission/not-found/busy/overconstrained errors, overlapping requests, track-ended, unsupported, and Docs-safe playground. Do not claim the hook analyzes audio levels.
- For WebSocket examples (`useWebSocket`): keep exactly one **Live connection** story with a user-editable `wss://` URL and manual Connect — Docs must not auto-connect, and the play test must inspect idle UI only (never initiate real network activity). Every other story uses a Storybook-only `webSocketMock` that patches `globalThis.WebSocket`, restores after uninstall, and covers dashboard, buffering, URL/protocol switching, reconnect/backoff/exhaustion, heartbeat success/timeout, binary payloads, errors, lifecycle unmount, and a mount-gated playground. Re-install during render after Strict Mode cleanup; never ship the mock in `dist`/tarball; prefer controlled mock events and `waitFor` over multi-second sleeps.
- For local-storage examples (`useLocalStorage`): namespace every demo key (`muradyanvano-react-hooks:useLocalStorage:…`); never store secrets; clean keys after every play test and restore clipboard/storage mocks. Primary **Persistent fruit editor** should show form fields, serialized preview, Saved locally, Reset/Remove, and a CSS fruit icon (no external artwork). Cover preferences/`mergeDefaults`, counter remount, boolean/string/object/array, Date/Map/Set serializers, custom serializer, merge compare, two-component sync, simulated cross-tab `StorageEvent`, dynamic key, writeDefaults, malformed repair, restricted storage, remove vs reset, custom iframe window, and a Docs-safe mount-gated playground. Prefer `waitFor` + deterministic events over real reloads or second browser tabs.
- For session-storage examples (`useSessionStorage`): namespace keys (`muradyanvano-react-hooks:useSessionStorage:…`); never store secrets; clean session (and local when showing isolation) after every play test; restore mocks/iframes. Primary **Checkout draft** should show step indicator, contact/delivery controls, “Saved for this tab”, raw preview, remount, Reset/Discard. Cover wizard, tab workspace, temporary form, counter/boolean/object/array, Date/Map/Set, custom serializer, mergeDefaults, two-component sync, local/session isolation, related-context (not ordinary separate-tab) `StorageEvent`, dynamic key, writeDefaults, malformed repair, restricted storage, remove vs reset, custom iframe window, and a Docs-safe mount-gated playground.
- For session-storage examples (`useSessionStorage`): namespace keys (`muradyanvano-react-hooks:useSessionStorage:…`); never claim ordinary separate tabs share session state; primary **Checkout draft** should show multi-step checkout UI with remount, Reset/Discard, and “Saved for this tab”. Cover wizard/workspace/temporary form, serializers, merge, two-component sync, local/session isolation, related-context simulated session `StorageEvent`, dynamic key, writeDefaults, malformed, unavailable, remove vs reset, custom iframe window, and mount-gated playground. Clean both storage areas when demonstrating isolation.
- For cookie examples (`useCookies`): use valid cookie-name tokens (`rh_uc_…` — no `:`); never store secrets; clean with matching path/domain after every play test; restore document/timer/cookieStore mocks. Primary **Locale preferences** should show language/currency selectors, region summary, cookie table, raw `document.cookie`, and reset/remove. Cover basic/all/JSON/doNotParse/attributes/theme/consent/dependencies/auto-deps/two-components/external/polling/cookieStore/removal-path/error/unavailable/SSR-initial/custom-document/listeners/playground.
- For JWT examples (`useJwt`): use only synthetic demonstration tokens (never production credentials); keep private Storybook token helpers out of `dist`; primary **JWT inspector** must show editable token input, header/payload/signature segments, JSON panels, claims table, and a prominent “Decoded only — signature not verified” warning; cover typed claims, Unicode, token editor, fallback, invalid structure/Base64URL/JSON, expiration/nbf/iat display (clearly not validation), audience/issuer, algorithm warning (`alg: none`), dynamic accounts, error callback timeline, SSR-safe decoding, and a Docs-safe mount-gated playground; never describe decoding success as authenticated/verified/trusted.
- For long-press examples: use Pointer Events; show accessible click/keyboard alternatives for every meaningful action; do not claim the hook returns progress state; avoid accidental click/long-press double actions; use short story-specific delays in browser tests with deterministic `waitFor`; document that click is not auto-suppressed; keep `touch-action` / focus rings intentional.
- For viewport hit-testing examples (`useElementByPoint`): `x`/`y` are always client (viewport) coordinates, the same space as `event.clientX`/`clientY` and `element.getBoundingClientRect()` — never page/document coordinates. Drive demos from real pointer events (`onPointerMove` reading `event.clientX`/`clientY` directly) or from `getBoundingClientRect()`-derived centers of real target elements via "Move to …" buttons, not from hand-picked numeric literals. Highlight overlays and crosshairs are Storybook-only sibling nodes positioned from `getBoundingClientRect()` (overlay via `position: absolute` inside the story's relative stage, using the target rect converted into the stage's local coordinate space; a canvas-drawn crosshair converts client coordinates into the canvas's own devicePixelRatio-scaled drawing space) — both carry `pointer-events: none` so they are provably excluded from hit testing (`document.elementFromPoint` skips `pointer-events: none` elements) and never mutate the detected element. Demonstrate `multiple: true` by filtering `elementsFromPoint`'s full ancestor-chain result (which includes containers up to `<html>`) down to the story's own known elements before rendering a list. Demonstrate `update()` with a fixed, one-time coordinate and a target moved only via CSS (no coordinate change) so the memoized result visibly goes stale until `update()` is called — do not combine this with `pause()`, since `update()` is a no-op while paused. For a custom-`document` example, use a same-origin `<iframe srcDoc>` fixture, read `event.currentTarget.contentDocument` from `onLoad`, and show an honest "waiting for the iframe" fallback before it is ready; remember that coordinates inside that document are relative to the iframe's own viewport, not the parent page's.
- For observer-based hooks, demonstrate external or imperative DOM mutation accurately. Do not fake detection through ordinary conditional React rendering when that behavior is not guaranteed.
- For hover-tracking examples (`useElementHover`): the primary **Hover me** story must show two adjacent buttons both starting with the exact label `Hover me` — one immediate and one with `delayEnter: 1000` in the consumer snippet. Show live boolean status for each. Use semantic buttons; keep essential content available without hover; document that keyboard focus does not change the hook boolean. Browser tests may use a shorter test delay via a dedicated story. Delayed-leave demos must wrap trigger and related panel in one observed ref. Removal demos should actually remove the target from the DOM when demonstrating `triggerOnRemoval`.
- For direct-focus examples (`useFocus`): the primary **Focus controls** story must include a `tabIndex={0}` paragraph labeled `Paragraph that can be focused`, a search input, a `Button that can be focused`, status text including `The input control has focus`, and three command buttons with exact labels `Focus text`, `Focus input`, and `Focus button`. Do not auto-focus on Docs load — gate `initialValue` behind explicit mount toggles. Keep visible focus rings; pair with `useFocusWithin` for container-level examples.
- For focus-within examples (`useFocusWithin`): the primary **Focus in form** story must attach `useFocusWithin` to a form ref, show exact status `Focus in form: false` / `Focus in form: true`, include labeled fields `First Name`, `Last Name`, `Email`, and `Password`, and provide an outside focus control. Browser tests must move between fields without a false status transition. Explain that DOM portals outside the subtree do not count.
- For infinite-scroll examples (`useInfiniteScroll`): the primary **Infinite list** story must start with six items, use `distance: 10`, load asynchronous batches, stop via `canLoadMore`, show loading/`All items loaded`, and expose Reset that restores the initial list and calls `reset()`. Keep Docs from auto-loading (gate playground mounting). Prefer isolated iframe documents for window/document demos. Include keyboard-focusable scroll regions, `aria-busy`, restrained live updates, and reachable reset/retry controls in examples only — the hook itself does not manage focus or announcements.
- For mouse-coordinate examples (`useMouse`): the primary tracker must use a contained surface with a `pointer-events: none` marker, live `x`/`y`/`sourceType`, and default page-coordinate behavior. Keep markers and grids decorative (`aria-hidden`). Prefer restrained live-region summaries over announcing every mousemove. Isolate page-scroll demos in a same-origin iframe. Demonstrate custom extractors for element-relative coordinates, `dragover` updates, touch reset, `eventFilter` scheduling with consumer-owned cleanup, and a Docs-safe playground without a page-level cursor overlay.
- For mouse-pressed examples (`useMousePressed`): the primary **Press and hold** story must use a tactile pad driven only by hook state, explain that release is tracked globally, and browser-test press inside / release outside. Include mouse-only, touch, drag, callback counters, capture toggle, enabled toggle, dynamic target, initial-value mount gate, and a Docs-safe playground/window demo without page-level overlays. Do not present generic press surfaces as keyboard-accessible buttons.
- For parallax examples (`useParallax`): the primary **Layered scene** must use an original local multi-layer illustration with different depth multipliers, live roll/tilt/source text, overflow-hidden stage, and `prefers-reduced-motion` restraint. Simulate device orientation with controlled events — never open native permission prompts in Docs or play tests. Document that consumers own transforms and reduced-motion behavior. Include mouse-normalization, screen-rotation, clamp, SVG target, permission-guidance (mount-gated), and Docs-safe playground stories.
- For scroll-tracking examples (`useScroll`): the primary **Scroll dashboard** must use a contained 2D scroll area (overflow auto, fixed height, not page scroll) with corner labels, live x/y/isScrolling/arrived/directions, X/Y inputs calling setX/setY, Smooth toggle, Measure button, offset boundaries, and minimap. Gate window/document iframe demos behind onLoad + enabled. Include vertical/horizontal galleries, throttle/idle/onStop, programmatic scroll, mutation observation, RTL horizontal, dynamic content/target, enabled toggle, error handling, and Docs-safe playground stories. After imperative `ref.current` assignment, include a commit/state signal when needed.
- For scroll-lock examples (`useScrollLock`): the primary **Scroll lock** story must use a contained 2D scroller (TopLeft/TopRight/BottomLeft/BottomRight + central “Scroll Me”), show `isLocked`, and keep Lock/Unlock (`toggle()`) outside the scroll region with a subtle locked badge while preserving scroll position. Prefer isolated iframe documents for window/document/modal page-lock demos so Storybook Docs is never locked. Modal demos need an accessible dialog (focus in, Escape/close restores, focus back to trigger). Cover multiple owners, `initialLocked` mount gates, existing/`!important` overflow restore, dynamic and late targets, SVG targets, scroll-position and unrelated-style preservation, unmount cleanup, and a Docs-safe playground. Finish every play unlocked/clean; use `role="region"` + `aria-label` on scrollers and `tabIndex={0}` only when keyboard scrolling is intended.
- After imperative `ref.current` assignment in examples, include a small commit/state signal when needed so observation can sync, and keep the snippet honest about that requirement.
- Hide Storybook autodocs source when the custom code panel already shows the consumer snippet.
- Highlight TSX with Shiki (or an official Storybook Source block if it meets the same bar). Keep highlighters development-only.
- Add meaningful `play` interaction tests and accessibility checks for important stories, including disclosure and clipboard behavior.
- Keep examples responsive across mobile, tablet, and desktop viewports.
- Provide clean consumer source snippets that match the public API and do not claim npm publication.
- Example styling may use Tailwind; the hooks package must not require Tailwind.
- Light-only design. Do not add dark mode or theme switching.
- Tailwind, Storybook, and syntax highlighters stay development-only and must never enter the library bundle or npm tarball.
- Do not invent empty sections for hooks that do not exist yet.
- When public hook behavior changes, update the related stories and docs in the same change.

When architecture, conventions, API behavior, package usage or testing policy changes, update this skill if its instructions become stale.
